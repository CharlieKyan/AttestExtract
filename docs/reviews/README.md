## 每次如何交付

1. 开始修改前记录基准提交和工作区已有改动；用户明确指定比较对象时，以指定对象为准。
2. 完成一项可交付改动后，复制 [TEMPLATE.md](TEMPLATE.md)，命名为 `YYYY-MM-DD-topic.md`。同日多项改动使用不同主题名。
3. 审查实际 Diff，按六项填写摘要，重点解释行为差异；保留实际检查证据，未执行项明确标记。
4. 需要独立审阅时，记录真实来源和范围；发现问题后若又修改实现，应更新摘要和相关验证，避免留下已过时的结论。
5. 更新本页索引，按照已有发布流程提交；聊天最终回复给出摘要和本页链接。

每次指一项完成的任务，不是每次保存文件，也不要求每次建新包版本。
纯文档改动可以精简六项内容，函数变化和代码审查位置可说明不适用。

## 版本与证据约定

- 摘要写明基准 SHA、目标提交或固定标签、审查方式及包含／排除的改动。若基准不明，先记录边界，不能声称已完整审计。
- 同提交保存摘要时，可以使用本次固定标签作目标，避免引用尚未产生的自身提交号。无标签时，可在后续文档提交中指向已存在的被审查提交，并明确文档维护范围。
- 历史代码链接绑定目标提交或标签，例如 GitHub 的 `blob/<固定引用>/path#L行号`。本地交付可另提供绝对文件路径和行号；后续版本不要覆盖旧摘要。
- 摘要顶部先给结论，正文沿用六项模板。严重问题给出代码位置、触发条件和影响；没有证据支持的问题不凑数量。
- 测试记录本次实际执行的命令或检查方式、结果及未覆盖场景。历史结果、模拟与真实调用分别标注；CI 尚未完成就写待完成，后续实时状态通过相应提交的 CI 链接查看。
- 公开文档不复制真实论文、批注、模型原始输出、凭据或私有日志；必要的研究验证仅提供可公开的汇总结论。

目前通过仓库指令要求交付摘要，尚未增加“缺少摘要即失败”的 CI 检查，也未改为每次必须建立 PR 或 Release。现有 CI 继续执行既有测试和安装验收。
